# BRIEF: Multi-source fallback for archive downloads

## Status

Accepted

Framing for issue #2443. The downstream PRD owns the requirements
articulation; the DESIGN owns where the source list lives in the recipe
schema and the plan format.

Two framing questions were open during drafting and are handed to the PRD's
Decisions and Trade-offs section rather than settled here: whether the ordered
list arrives as a new parameter alongside `url` or as a widened `url` that
accepts a string or an array, and whether install-time fallback must be
behaviourally identical to plan-time fallback or may be best-effort when a
plan was generated by an older tsuku that recorded only one source.

## Problem Statement

A tsuku recipe can name exactly one host for a download. The recipe schema
has a single `url` string on `download_archive` and its three siblings, and
nothing anywhere in `internal/actions/` or `internal/recipe/` accepts a list.
So the set of hosts that can serve a given tool's bytes is always one, chosen
once by whoever wrote the recipe, and changing it is a code change.

That would be a mild inconvenience if the cost of a dead host were a failed
install. It isn't. `download_archive` fetches the whole archive during plan
generation to compute the checksum it pins, so an unreachable host fails
`tsuku eval` — plan generation, not installation. And because zig is an
implicit build-time dependency of `cmake_build`, `configure_make` and
`meson_build`, a single dead zig host turns `Validate Embedded Dependencies`
red on every pull request that touches `recipes/`, whether or not that PR has
anything to do with zig. One operator's outage becomes the whole repository's
CI outage.

Two properties make the current shape worse than a normal single-point-of-
failure. The first is that the only available repair is a maintainer editing
a recipe and merging it, so the recovery time for an outage is however long it
takes a human to notice red CI, triage which host died, find a replacement,
and prove the replacement is reachable from GitHub runners. The second is that
the repair does not reach anything already published: `scripts/r2-upload.sh`
publishes generated plans to R2 and sandbox and validation images install from
those plans weeks later, so every plan generated before the swap still names
the dead host and no recipe edit can touch them.

The pattern is established rather than hypothetical. `ziglang.org` was
intermittently unreachable from CI (#2384) and was replaced with
`zigmirror.hryx.net` (PR #2391). `zigmirror.hryx.net` became unreachable
entirely (#2441) and was replaced with `ziglang.freetls.fastly.net`
(PR #2444). Each round improved the choice of host and left the shape
untouched, so each round bought time rather than fixing anything. The
follow-up work was identified both times; the first time it was recorded only
in a pull request description, was never filed as an issue, and was forgotten
in time for the second outage to land on another single-host swap.

## User Outcome

A recipe author who knows a tool's archives are served from more than one
place can say so in the recipe, and tsuku uses that knowledge on its own.

For the recipe author, the change is that host choice stops being a single
irreversible commitment made at authoring time. They list the hosts they trust
in preference order, and the recipe stops needing an edit every time one of
them has a bad week.

For everyone waiting on CI, the change is that a single host going down stops
being an event. Plan generation tries the next source and produces the same
plan it would have produced anyway — the checksum is a property of the bytes,
not of the host that served them, so nothing downstream can tell which source
answered.

For a user installing from a plan published weeks ago, the change is that the
plan carries the whole list rather than the one host that happened to answer
during generation. They get the same fallback the maintainer had at plan time,
in the situation where they have the least ability to do anything else: they
cannot regenerate the plan and they cannot edit the recipe.

For a maintainer triaging an outage, the change is that "which host died" stops
being an urgent question. It becomes a question about whether the list still
has enough healthy entries to be worth topping up, answerable on a normal
working day.

## User Journeys

### A recipe author declares several sources

The author is writing or revising a recipe for a tool whose upstream publishes
a mirror list — zig is the live example, with `community-mirrors.txt` on
ziglang.org. Today they read that list, pick one entry, and paste it into
`url`. The trigger for this journey is that same authoring moment. The outcome
shape is that they write the hosts they trust in preference order and the
recipe records all of them; validation checks every entry rather than only the
first, so a typo in the third source is caught at authoring time and not
during an outage two months later.

### CI survives a dead first source

The user is whoever opened a pull request touching `recipes/` — most often
someone with no connection to the affected tool. The trigger is
`Validate Embedded Dependencies` running plan generation for a recipe whose
first source is unreachable from the GitHub runner. Today the job fails and
the PR is blocked until a maintainer lands a recipe edit. The outcome shape is
that plan generation moves to the next source, emits a plan identical to the
one the first source would have produced, and the job passes. The contributor
never learns there was an outage.

### A published plan outlives its first source

The user is installing a tool from a plan published to R2 some weeks earlier —
a sandbox image, a validation container, anyone running `tsuku install --plan`.
The trigger is that the host recorded in the plan has gone down in the
meantime. Today the install fails with nothing the user can do: they cannot
regenerate the plan and editing the recipe would not change the published
artifact. The outcome shape is that the plan carries the ordered list the
recipe declared, the install falls through to a live source, and the pinned
checksum verifies exactly as it would have against the first one.

### A maintainer triages an outage that no longer blocks anything

The maintainer is responding to a report that one of a tool's sources is
returning errors. The trigger is the report, not a red build — CI is passing,
because the other sources answered. Today the same report arrives as a
repo-wide CI failure and forces an immediate swap. The outcome shape is that
they check whether the remaining sources are healthy, decide whether the list
needs topping up, and land the change on a normal schedule.

## Scope Boundary

### In

- A recipe can declare an ordered list of download sources for
  `download_archive`, and for the sibling actions that share the same
  download funnel (`github_archive`, `github_file`, `fossil_archive`),
  since the funnel is shared and a change that reaches only one of them
  would invite a fork.
- Plan generation tries the declared sources in order and succeeds when any
  one of them serves the bytes.
- The generated plan records the full ordered list, not only the source that
  answered, so install-time fallback survives publication.
- Install-time download falls back across the recorded list the same way plan
  generation does.
- Recipe validation and action preflight cover every declared source, so
  validation that applies to the first entry applies to the rest.
- Behaviour is unchanged for a recipe declaring a single source: same
  validation, same generated plan, same install.
- `internal/recipe/recipes/zig.toml` uses the mechanism, with the current
  Fastly source first.
- Golden-plan handling for multi-source recipes is defined and documented.

### Out

- **Zig's community-mirror protocol.** Fetching `community-mirrors.txt` at
  plan time, ranking its entries, and falling back to the canonical host is a
  zig-specific capability that generalizes to nothing else. A per-recipe list
  covers zig and every other recipe; the protocol covers zig.
- **A hostname-keyed mirror registry in Go.** Which host serves a given
  project's archives is knowledge the recipe owns. A registry inside the CLI
  puts host policy where recipes cannot see it.
- **The R2 golden publish/consume pipeline (#2448).** Registry goldens are
  currently published to a layout no consumer reads, so nothing validates
  them. Real, related, and separately tracked — this work must not depend on
  that pipeline for its safety net.
- **Making plan generation stop downloading archives.** `Decompose` fetches
  the entire archive purely to compute a checksum the goldens already pin, and
  `--pin-from` does not pin it. Fixing that would make an unreachable source
  harmless even with zero fallback, which is a cheaper fix for the CI symptom
  and a different piece of work.
- **Re-litigating zig's current first source.** Fastly was chosen in #2441
  with CI evidence of reachability from GitHub runners. This work makes the
  single-source question moot; it does not reopen the choice.
- **Automatic source discovery or health ranking.** Sources are declared by
  the recipe author in a fixed order. Probing hosts, reordering by latency, or
  remembering which one worked last time are all deliberately excluded — they
  would make plan generation depend on network conditions.
